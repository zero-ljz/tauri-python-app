# tauri-python-app

Tauri v2 desktop app with a React/TypeScript frontend, Rust bridge layer, and Python backend runtime.

## Tech Stack

- Frontend: React, TypeScript, Vite, MobX, shadcn/ui, Tailwind CSS v4, Lucide
- App shell: Tauri v2
- Rust bridge: Tauri commands, backend lifecycle, JSON-RPC request tracking
- Python backend: Python 3.10, asyncio, pydantic, PyInstaller
- Transport: stdin/stdout NDJSON framed JSON-RPC 2.0

## Architecture

```text
React UI
  -> Tauri invoke / event listen
Rust bridge
  -> backend process lifecycle
  -> JSON-RPC request/response matching
  -> stderr log forwarding
Python backend
  -> asyncio stdin reader
  -> dispatcher
  -> task runtime
```

## Protocol Notes

- `stdout` only carries JSON-RPC/notification NDJSON protocol messages.
- `stderr` only carries logs; Rust forwards them to the frontend debug panel.
- Process spawn and protocol readiness are separate states. Rust accepts RPC only after `backend.ready`.
- Backend lifecycle uses generations so late events from an old process cannot corrupt a restarted process.
- Dotted protocol methods are mapped to slash-separated Tauri events, e.g. `task.progress` -> `backend://task/progress`.
- Short operations use request/response.
- Long-running operations return a `task_id`, then push status, progress, and result notifications.
- Pydantic models are the schema source of truth; TypeScript types are generated by `scripts/gen_types.py`.

## 开发流程

### 前端开发

启动完整应用：

```bash
pnpm tauri dev
```

调试面板入口：

- 菜单栏 -> 视图 -> 显示 IPC 调试面板
- 偏好设置 -> IPC 调试面板

RpcDebugPanel 包含：

- 报文：前端 request/response/notification 历史
- 日志：Python backend stderr 实时日志和启动日志回放
- 请求：手动发送 JSON-RPC 请求

### 新增 Python RPC handler

1. 在 `backend/handlers/` 下新增或修改 handler。
2. 使用 `@rpc.register("method.name")` 注册方法。
3. 如果新增了文件，在 `backend/main.py` 中 import 它，确保装饰器执行。
4. 如果涉及新数据结构，更新 `backend/models.py`。
5. 运行：

```bash
pnpm gen:types
pnpm build
```

示例：

```python
from backend.rpc import rpc

@rpc.register("echo")
async def handle_echo(params: dict) -> dict:
    return params
```

### 任务运行时

任务分两类：

- async I/O 任务：`TaskRegistry.submit_async(...)`，内部使用 `asyncio.create_task`
- 阻塞 I/O 任务：`TaskRegistry.submit_blocking(...)`，内部使用 `loop.run_in_executor + ThreadPoolExecutor`

注意：

- async 任务可以正常取消。
- blocking 线程任务不能强制杀掉，只能记录取消意图并返回 `cancelled=false`。
- 纯 Python CPU 密集型任务不要放在线程池；GIL 会限制并行能力。此类任务应使用独立 process worker。
- Tauri 关闭时会主动终止 sidecar；stdin EOF 也会触发 Backend 的确定性退出，运行中的线程任务不会残留为孤儿进程。

## Backend 打包

Tauri 发布配置使用：

```json
"externalBin": ["bin/backend"]
```

实际文件名由 Tauri target triple 决定，例如 Windows：

```text
src-tauri/bin/backend-x86_64-pc-windows-msvc.exe
```

手动构建 backend：

```bash
pnpm build:backend
```

指定 target：

```bash
python scripts/build_backend.py --target x86_64-pc-windows-msvc
```

PyInstaller 不是交叉编译器。`--target` 必须与当前 `rustc` host triple 完全一致；
其他系统或 CPU 架构必须在对应的原生 CI runner 上构建。仓库 CI 会在
Windows、macOS 和 Linux 分别生成并检查各自的 sidecar。

清理 PyInstaller 缓存后构建：

```bash
python scripts/build_backend.py --clean-cache
```

`src-tauri/bin/*.exe` 是本地构建产物，默认不提交到 Git。发布构建时会自动重新生成。

## 类型生成

类型来源：

```text
backend/models.py
```

生成输出：

```text
src/types/generated.ts
src/types/schema.json
```

命令：

```bash
pnpm gen:types
```

`src/types/schema.json` 是中间产物，默认不提交。`src/types/generated.ts` 包含 DTO、
`RpcMethodMap`、方法参数和返回值映射，前端业务调用优先使用类型安全的 `rpcCall(...)`。

## JSON-RPC 约定

request:

```json
{"jsonrpc":"2.0","id":"request-id","method":"echo","params":{"message":"hello"}}
```

success response:

```json
{"jsonrpc":"2.0","id":"request-id","result":{"message":"hello"}}
```

error response:

```json
{"jsonrpc":"2.0","id":"request-id","error":{"code":-32601,"message":"Method not found"}}
```

notification:

```json
{"jsonrpc":"2.0","method":"task.progress","params":{"task_id":"...","progress":0.5}}
```

已处理的协议错误：

- `-32700 Parse error`
- `-32600 Invalid Request`
- `-32601 Method not found`
- `-32603 Internal error`

## 安全策略

Tauri CSP 配置在 `src-tauri/tauri.conf.json`：

- `csp` 用于生产构建，限制脚本、连接、图片和字体来源。
- `devCsp` 用于开发环境，额外允许 Vite HMR 需要的 localhost/ws 和 inline dev script。

不要随意改回 `csp: null`。如果新增远程资源，需要同步评估 CSP 和能力权限。

能力权限在 `src-tauri/capabilities/default.json`。WebView 只保留必要窗口控制权限。
Sidecar 仅由受信任的 Rust 层管理，因此不向前端开放 shell spawn/kill/stdin 权限。

## Backend 生命周期

- 状态：`stopped -> starting -> ready -> stopping`，启动失败进入 `failed`。
- `backend_status` 返回可重放的状态快照、版本、能力列表和最近错误，不依赖一次性事件。
- Backend 异常退出后前端最多自动重试三次，使用指数退避。
- 可通过 `backend_start`、`backend_stop`、`backend_restart` 显式控制。
- 开发构建默认运行源码 Backend。设置 `TAURI_PYTHON_BACKEND_MODE=sidecar` 可强制调试构建运行打包后的 sidecar，用于复现 release-only 问题。
- Backend 工作目录固定为系统应用数据目录；业务代码应使用 `TAURI_APP_DATA_DIR`，不要依赖启动目录。

## 排障

### DevTools 里看到 `http://ipc.localhost/...`

这是 Tauri IPC 的 DevTools 表现，不是访问外网。正常情况下不应持续刷旧的窗口轮询请求。

### `Backend 进程尚未运行，RPC 请求已取消`

常见原因：

- Python 解释器不可用
- `.venv` 里缺少依赖
- `backend/main.py` 启动异常
- 打包后的 backend 二进制不存在或过期

处理：

```bash
python -m backend.main
pnpm build:backend
pnpm tauri dev
```

同时打开 RpcDebugPanel 的“日志”页签查看 backend stderr。

### 模拟发送请求超时

先确认 backend 是否已 ready，再检查“日志”页签。如果是协议错误，Python backend 应返回 JSON-RPC error，而不是静默超时。

### 发布包 backend 不工作

先验证 backend 二进制：

```bash
pnpm build:backend
```

再验证 Tauri 构建链：

```bash
pnpm tauri build --debug --no-bundle
```
